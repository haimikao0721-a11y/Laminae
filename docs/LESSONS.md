# 踩过的坑

[中文](LESSONS.md) | [English](LESSONS.en.md)

按时间倒序。每一条都写清三件事：**症状**、**根因**、**改了什么**。

分两类：一类是**工具的缺陷**（会诬告、会漏、会崩），一类是**我自己的操作失误**（不是产品 bug，但同样是坑，而且更容易重复踩）。

---

## 一、工具的缺陷

### 孤立模块把入口脚本当缺陷（click，15 条全错）

**症状** 在 click 上报出 15 个孤立模块，人工核对 **15 条全错**：12 条在 `examples/` 下（给人 `python xxx.py` 跑的示例）、2 条在 `docs/` 下（Sphinx 加载的配置）、1 条是 `src/click/testing.py`。

**根因** 判据是「没有任何模块 import 它」。这在库项目里几乎总是错的——**一个模块没有内部引用，常常意味着它是出口，不是入口**。`click/testing.py` 提供 `CliRunner`，是给使用者用的，库自己当然不 import 它。

**改了什么** 改为从仓库里明写的声明取证，认到一种就排除，理由一并输出：目录角色（`examples/` `docs/` `scripts/` `bin/`）、Python 包归属（同级有 `__init__.py`）、清单声明（`package.json` 的 `bin`/`main`、`pyproject.toml` 入口点、`Cargo.toml` 的 `path`）、文件开头 `#!`。click 15 → 0，archify 4 → 3（少的那条有 `#!`，是脚本）。

**教训** 「没有入边」是结构事实，不是缺陷。把它当缺陷，等于把人体的「血压没有被引用」判成有病。

---

### 往下看一层把历史当现在（click，53/100）

**症状** 报出 100 条「需要人工复核」，其中 53 条只存在于 2014 年的 `click.py`（后来拆成 `src/click/`），在 HEAD 上早已不存在。

**根因** `unreferenced`/`down` 都是按 commit 记的，`intervals()` 会把「曾经成立」的区间全留下。列表按时间顺序排，截前 40 条——**看到的全是历史噪声，真正还在的问题排不进去**。

**改了什么** 每条算一个 `atHead`，看它的 `alive` 区间盖不盖得住最后一个提交。历史条目折进 `<details>`，默认收起但可展开查。

**教训** 折叠而不是删除。「这里曾经有过、后来没了」本身是信息，它说明这条路被修过。

---

### 测试和示例里的空函数当缺陷（click，45/47）

**症状** 修掉历史噪声后，剩下 47 条「当前成立」里，**45 条在 `tests/`、2 条在 `examples/`，`src/` 里一条都没有**。

**根因** 测试里的桩函数（`def f(): pass`）、示例里的空 CLI 是**写法本身**，不是缺陷。

**改了什么** 标记调用链和空实现两处都跳过测试文件与 `examples`/`docs`，和孤立模块共用同一个 `ENTRY_DIR`。click 当前成立 0 条，历史 48 条。

**教训** 和第一条是同一件事：把「本来就是这样的」当成「有问题」。

---

### 孤立模块没按「现在还成立」筛（vue，119/170）

**症状** vue 上报出 170 条孤立，其中 **119 条在 HEAD 上根本不存在**——早期路径，后来改名或移走了。

**根因** 和「往下看一层」完全同一个毛病。那里加了 `atHead`，**这里漏了**。

**改了什么** 同一个 `aliveNow` 判据。170 → 31。

**教训** 一个修正在一处生效，不代表同类问题在别处也修了。**修完要问：这个毛病还有没有别的地方犯。**

---

### 被工具按名字加载的文件当孤立（vue，27/31）

**症状** 筛掉历史之后剩 31 条，全是新面孔：`vitest.config.ts`、`eslint.config.js`、`vite.config.ts`、`__benchmarks__/*.bench.ts`、`dts-test/*.test-d.ts`。

**根因** 它们从不被应用代码 import，但**每一个都是活的**——工具按文件名/后缀/目录名找它们。

**改了什么** 加 `TOOL_LOADED` 与 `BENCH_DIR` 两条规则。判据是后缀和目录名，**不是猜**——vitest、eslint、vite、tsc 确实就是这么找的。31 → 4。

**教训** 每换一个生态就会冒出一批新的「按约定加载」。这是这一档的固有成本，只能一条条补，但每条都要能指到「工具真的这么找」。

---

### 规则写错时诬告成「文档是假的」

**症状** locator 的捕获组多带一个字符（把反引号写进了括号里，捕获到 `docs/help.md` 后面多一个反引号），文件其实存在，却判成假。

**根因** 捕获到的文本直接拿去查路径，多一个字符就查不到。

**改了什么** 两个独立标签，都不改判定：`ruleMiss`（locator 在整段历史里一次都没匹配到）、`captureHint`（去掉首尾标点后同名文件确实存在）。用黄色不用红色——**这不是「假」，是「没测准」**。

**教训** 一个会诬告的检查比不检查更糟：用户会开始不相信红色。

---

### `ruleMiss` 的第一版判断写错了

**症状** 逻辑上写的是「locator 一次都没匹配到」，实际一条都没报出来。

**根因** 写成了 `verbatimRuns.length === 0`。但 locator 永不匹配时，`verbatimRuns` **不是空数组，而是每一段 `text` 都是 `null`**。

**改了什么** `verbatimRuns.length === 0 || verbatimRuns.every((x) => x.text === null)`。

**教训** 「没找到」有两种形态：容器为空，和容器里全是空值。测试立刻抓到了这一条。

---

### 说法写不出来却静默判成「尚未写入文档」

**症状** 一条 `regex-count` 说法的 locator 捕获到 `8.6.0`（版本号），读不成数，于是每条 commit 都判成「尚未写入文档」。**文档明明白白写着 8.6.0，却被告知「没说这件事」。**

**根因** 数字类事实要拿捕获文本去比数，`parseClaimedNumber("8.6.0")` 返回 `null`，状态落到缺席。

**改了什么** 新增说法体检（`lint.ts`），跑之前先查三类：捕获读不成数、locator 在基准提交上一处都匹配不到、`fact` 里写了该类型不认的字段。

**教训** 静默降级比报错更糟。报错至少告诉你「这里有问题」，静默降级让你以为「这里没有问题」。

---

### `fact` 里写了该类型不认的字段，被静默丢掉

**症状** 在 `fact` 里写了 `"compare": "gte"` 和 `"claim": 5`，两个字段一个都没生效，也没有任何提示。

**根因** `parseFact` 是**重建对象**的，不认的字段直接丢弃。

**改了什么** 体检里查 `fact` 的字段白名单，写了多余的字段就报，并把「这个类型只认哪些」列出来。

**教训** 任何「读进来再重建」的地方都会静默丢信息。

---

### 一条注定跑不到的死代码

**症状** 体检里本来还想查「引用型事实配 `compare` 没有意义」。

**根因** 写测试时发现 `parseClaims` **已经直接抛错了**，比警告更硬。

**改了什么** 删掉。

**教训** 不在库里留一个跑不到的功能冒充检查能力。

---

### 一个从不失败的检查等于没有检查

**症状** 校验器写好后，在 click 上一直通过。

**根因** 没验证过它会不会失败。

**改了什么** 造了两次假：手改 HTML 里的一个数字、伪造 payload 的汇总数。两次都被抓住，且定位到具体字符位置和那一行。同时补了「渲染器指纹」——报告由旧版渲染器生成时只警告、跳过逐字节比对，**否则改一次样式，所有旧报告都会被判成造假**。

**教训** 校验器自己也要被校验。而且**不能喊狼来了**，喊多了就没人看。

---

### Rust 模块：`looksLike` 用 `=>` 排除 JS

**症状** 一半 Rust 文件被当成 JS 处理，函数一个都识别不出来。

**根因** 判据写的是「有 `fn` 且没有 `function(` 和 `=>`」。但 **Rust 的 `match` 分支也用 `=>`**。

**改了什么** 只看 `fn name(` 与 `function name(`。

**教训** 用「另一个语言的语法特征」做排除，很容易撞车。

---

### Rust 模块：空函数体被当成空壳

**症状** 报出 13 个「空实现」，全是 trait 默认实现（`fn quitting(&mut self) {}`）。

**根因** Rust 里空函数体是**常见写法**：trait 默认实现、标记实现、回调占位。

**改了什么** Rust 的 `empty` 不当作空壳；真正没实现的是 `unimplemented!()` / `todo!()`，那一档保留。`unreachable!()` 也不算——它是守卫，不是空壳。

**教训** 「空」在不同语言里含义不同。同一条规则跨语言套用会误报。

---

### Rust 模块：引用没接解析，图反而变小了

**症状** 加上 Rust 之后，引用图从 160 条边**掉到 19 条**，孤立模块从 9 **涨到 74**。

**根因** `.rs` 文件走进了 JS 的解析分支，`use crate::a::b` 一条边都没解析出来。

**改了什么** 补 `resolveRust`：`crate::a::b` 从 `src/` 往下找 `a/b.rs` 或 `a/b/mod.rs`，`super::` 往上、`self::` 当前。回到 185 条边、10 个孤立。

**教训** **这个错单跑测试发现不了**——得在真实仓库上看数字才会露出来。加一个语言，等于加一条没被验证过的路径。

---

### 目录搬家：`tsc` 全绿，测试挂了 8 条

**症状** 把 37 个模块分成六组之后，`tsc --noEmit` 通过，`npm test` 挂 8 条。

**根因** `run.ts` 的 `STEPS` 数组用的是**裸文件名**（`"measure.ts"`），路径在别处拼。按 `"src/"` 前缀写的替换规则完全覆盖不到。

**改了什么** 改成仓库相对路径（`"src/measure/measure.ts"`），并且加了一条测试：扫 `run.ts` 里的 `file: "..."`，每个都必须以 `src/` 开头且真实存在。

**教训** **字符串路径不是 import，`tsc` 查不出来。** 只有跑测试才会炸。

---

### 目录搬家：`SKILL_ROOT` 差一级

**症状** 同上那一轮。`SKILL_ROOT` 从 `path.resolve(HERE, "..")` 算出来，`HERE` 从 `src` 变成了 `src/core`，于是只退到 `src`。

**根因** 靠数 `..` 的层数算路径，文件一搬家就错，**而且错了不报错**——所有指向它的东西会静默指到别处。

**改了什么** 改成 `"../.."`，并加断言：仓库根必须有 `SKILL.md`、`package.json`、`src/`，且不许退过头（根上不该有 `types.ts`）。

**教训** 路径计算要么加断言，要么就别靠层数。

---

### 文档正文按 commit 全存，撞上 V8 上限

**症状** vue（6513 个提交）上流水线在第一步就死：`RangeError: Invalid string length`。

**根因** 每个 commit 存一份文档全文。vue 的 CHANGELOG 几百 KB，**6513 × 1 份 ≈ 1 GB**。

**改了什么** 正文按内容去重，`commits` 里存编号。**1 GB → 45 MB**。README 只有 55 个版本、CHANGELOG 315 个——大部分 commit 根本没动文档。

**教训** 规模问题不会在小仓库上暴露。click（1384 提交）跑得好好的。

---

### 注释和字符串里的代码样例被当成真代码

**症状** vue 上「往下看一层」报出一个叫 `xxx` 的空函数，还有 `NODE`、`foo`。查下去是两行注释：

```js
// Note: functions inside this closure should use `const xxx = () => {}`
// no: function NODE() {}
```

**根因** `findFunctions` 直接扫原文，不跳过注释和字符串。注释里写代码样例是很常见的写法，一命中的话 `hollowFunctions`、`delegatedCalls`、`classifyDepth` 全都跟着错。

**改了什么** 加 `maskNonCode`：把注释和字符串的**正文**替换成空格，保留长度和换行，也保留引号。长度不变是为了偏移不变——匹配出来的位置还能直接拿去切原文取行号。三个语法模块和 `delegatedCalls` 都改成扫遮罩后的文本。vue 当前成立 12 → 7。

**教训** 正则扫源码时，注释里的代码是最常见的一种假阳性来源。

---

### 类型声明文件被当成空实现

**症状** 剩下的 7 条里 4 条在 `dts-test` 下的类型测试文件 —— `declare function foo(...)` 被当成「函数体是空的」。

**根因** 类型声明文件里本来就不可能写到实现。**拿类型声明当代码看**。

**改了什么** `TYPE_ONLY` 正则，两处跳过条件都加上。

**教训** 第一版正则只认 `.d.ts`，匹配不到 `*.test-d.ts`（结尾是 `-d.ts` 不是 `.d.ts`）。测试立刻抓到。

## 二、我自己的操作失误

这些不是产品 bug，但**比产品 bug 更容易重复踩**，而且每一次都让我差点误判工具。

### 把状态编码读反，花了十几步验证一个不存在的 bug

**症状** 看到报告里 `states` 尾部是 `0`，认定「0 = 假」，于是断定工具诬告，写了 probe、跑了 lookup、查了 `judgeState`、翻了 `analyze.ts`。

**真相** **`0` 是真。** 证据就在旁边：`totalFalse=0`、`actual` 尾部是 `1,1,1`。我没看。

**教训** 拿一个没核对过的读数下结论，正是这个项目要防的那件事。**先看旁边有没有自相矛盾的数**。

---

### PowerShell 单引号里 `` `n `` 不是换行

**症状** 造测试仓库时写 `Set-Content "src\mid1.ts" '...`n...'`，文件成了一整行字面量 `` `n ``，还带 BOM。工具读到垃圾文本，一个函数都识别不出来。

**根因** PowerShell **单引号**字符串不做转义。

**改了什么** 改用 Node 写文件。

**教训** 我差点把这个报成工具的 bug。**先怀疑自己造的数据。**

---

### `Set-Content -Encoding UTF8` 加 BOM

**症状** `JSON.parse` 在 `--accept` 时失败。

**根因** PowerShell 5.1 的 `-Encoding UTF8` 写的是 **UTF-8 with BOM**。

**改了什么** 用 `[System.IO.File]::WriteAllText($p, $s, [System.Text.UTF8Encoding]::new($false))`；读的时候 `.replace(/^\uFEFF/, "")` 兜底。

---

### `>` 重定向写的是 UTF-16

**症状** `node x.ts > out.json` 之后 `JSON.parse` 读不了。

**根因** PowerShell 的 `>` 默认 UTF-16LE。

**改了什么** 给 `trace.ts` 加了 `--out` 参数，让它自己写 UTF-8 无 BOM。**这个坑对 agent 一样存在，所以封进工具里。**

---

### `.Contains()` 在 PowerShell 里对数组逐元素比

**症状** 判断 `LICENSE 里有 MIT` 得到 `False`，但文件里明明写着 `The MIT License`。

**根因** `git show` 的输出在 PowerShell 里是**字符串数组**，`.Contains("MIT")` 比的是「有没有一个元素正好等于 MIT」。

**改了什么** `-join "`n"` 之后再 `.Contains()`。

**教训** 同上——**预判错了会让我以为工具错了**。

---

### `git grep` 在非 git 目录静默返回空

**症状** 在 ElyOffice 的副本目录（不是 git 仓库）跑 `git grep`，得到「0 个 stub 标记」，差点报成「这个仓库很干净」。

**根因** `git grep` 不在 git 仓库里时**静默返回空**，不报错。

**改了什么** 换成直接 `Select-String` 扫文件。

**教训** 「查不到」和「查询失败」必须分开。这正是四态设计里 `测不出来` 那一档存在的理由。

---

### 探针脚本跑两次，把备份覆盖成坏版本

**症状** 为了验证「新测试能抓住问题」，临时把一条步骤路径改回裸名。探针脚本先备份再改——**但我跑了两次**，第二次运行时文件已经是坏的，于是**备份被覆盖成坏版本**，还原回去就是坏的。30 条测试挂掉才发现。

**改了什么** 用 `git checkout` 还原，而不是自己的备份。

**教训** 探针脚本要么幂等，要么还原走 git。

---

### 用缩进切代码块，切短了

**症状** 改 `layers-core.ts` 的调用链循环时，用「找到 `pending = next` 上面那个 `}`」来定边界。结果匹配到的是内层 `for` 的 `}`，切短了，留下语法错误。

**改了什么** 回滚，改用 `edit` 工具做精确文本替换。

**教训** 按缩进猜结构很脆。**有精确替换工具就别用脚本切块。**

---

### IIFE 在 `esc` 定义之前，导入即崩

**症状** 报告顶部的警告块写成模块顶层的立即执行函数，一导入就 `ReferenceError: Cannot access 'esc' before initialization`。

**根因** TDZ——`esc` 定义在那段之后。

**改了什么** 改成函数，模板里用到时才求值。

**教训** `tsc` 全绿。**是端到端测试抓到的。**

---

### 全量克隆 vs blobless 克隆

**症状** 先用 `--filter=blob:none` 克隆 click，跑了 178 秒还在读文件。

**根因** blobless 克隆下每次读文件都要走网络。

**改了什么** 量规模时用 blobless（快），跑流水线前换成全量克隆。

---

### 在错误的目录下跑校验

**症状** 在 click 目录下用 archify 的 run id 跑 `verify`，得到「先跑一次 run.ts」。

**教训** 每个仓库的校验必须在它自己的目录下跑。

## 三、反复出现的同一个毛病

回头看，工具的缺陷几乎全是同一句话的不同说法：

> **把「本来就是这样的」当成「有问题」。**

| 报出来的 | 实际是 |
|---|---|
| 15 条孤立 | 入口脚本、文档工具、库的公开 API |
| 100 条空壳链 | 53 条历史 + 45 条测试 + 2 条示例 |
| 170 条孤立 | 119 条历史路径 + 27 条工具按名加载 |

而**判定类**的输出（文档说 X，去核对 X）在真实仓库上从来没出过错。

这条分界线现在很清楚：

> **凡是「文档说了 X，去核对 X」的地方是准的。**
> **凡是「工具自己觉得这里有问题」的地方，都要先问一句「这东西按设计该不该是这样」。**

后者如果答不上来，就不该以「问题」的形态出现。
